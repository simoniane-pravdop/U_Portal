# Порядок розробки та розміщення

Чинне рішення користувача від 2026-09-26: основний портал —
https://up.automatizer.online на VPS. Подальші зміни після перевірки
публікуються в GitHub і на VPS. Старий Cloudflare-хостинг залишається
резервом без планового оновлення коду й без синхронізації даних.

## Основний цикл

Локальний проєкт → локальна перевірка → GitHub → резервна копія VPS-бази
→ оновлення тільки служби порталу → онлайн-перевірка → готово.

Код GitHub є джерелом версії застосунку. Не редагувати робочий код
безпосередньо на сервері. Дані й секрети не включати до Git або образу.

## 1. Локальна робота та перевірка

1. Перевірити стан Git і зберегти сторонні незавершені зміни.
2. Поточна гілка для VPS — `deployment/vps-copy`; працювати з її актуальною
   версією. Не надсилати зміни в `main`: на ній ще налаштовано автоматичне
   викладення Cloudflare. Зміна основної гілки потребує окремого узгодження
   та перевірки сценаріїв розгортання.
3. Внести зміну локально, перевірити відповідний сценарій на тестових даних.
4. Для змін коду виконати `npm test`, `npm run lint`, `npx tsc --noEmit`
   і `npm run build:vps`. Перевірити залежні сценарії та потрібні розміри
   екрана; масштаб перевірки відповідає зміні.
5. Зміни лише документації перевірити читанням, переглядом різниці та
   `git diff --check`; вони не потребують перескладання застосунку.
6. Не змінювати робочі картки й зовнішні задачі лише для перевірки без
   погодженої тестової дії.

## 2. GitHub і VPS

1. Переглянути різницю, створити зрозумілий коміт, передати його в
   `simoniane-pravdop/U_Portal` і перевірити відповідність комітів.
2. Перед оновленням застосунку зберегти й перевірити резервну копію бази.
3. Розгортати окремий випуск `/opt/u-portal/releases/<commit>` та образ
   відповідного коміту, використовуючи наявний SSH-псевдонім `juscript-vps`.
4. Оновлювати лише службу Docker Compose `u-portal-copy` / `portal`;
   база `/opt/u-portal/shared/data/portal.sqlite` залишається поза випуском.
5. Не змінювати Juscriptum, інші служби, їхні конфігурації або дані.
   Не виконувати загальне очищення Docker чи перезапуск VPS.
6. Порядок резервування й відкату наведено в `ops/vps/README.md`.
7. Для зміни лише цієї політики достатньо опублікувати файл у GitHub та
   `/opt/u-portal/DEVELOPMENT_WORKFLOW.md`; робочий контейнер не перезапускати.

## 3. Онлайн-перевірка та завершення

- Перевірити HTTPS, доступність порталу та відповідність розгорнутого коміту.
- Перевірити змінений сценарій, авторизацію й збереження даних, якщо вони
  зачіпаються зміною; переконатися у відсутності нових помилок.
- Перевірити, що https://www.juscriptum.online/api/health доступний.
- У разі помилки зберегти дані, повернути попередній сумісний випуск;
  не підміняти базу старим знімком без окремого рішення.
- Зміна коду завершена лише після GitHub, успішного VPS-розгортання та
  онлайн-перевірки. У підсумку називати фактичний результат і обмеження.

## Інтеграції та ресурси

На VPS особисті підключення Asana/Telegram, Google-вхід і планові зовнішні
дії після копіювання не налаштовані. Чинні збережені посилання залишаються
доступними. Активація інтеграцій потребує окремого налаштування для нового
домену й перевірки; зміна статусу сервера сама їх не активує.

Секрети VPS зберігати лише у захищеному серверному сховищі, не в документації,
Git чи журналах. Не додавати платні послуги, тарифи або ресурси без рішення
власника; враховувати ресурси інших проєктів на спільному VPS.

окремий знімок: він не є актуальною резервною копією подальших змін VPS.
Робочі зміни користувачі мають вносити лише на основному VPS-порталі.

Намір користувача — через місяць, орієнтовно 2026-10-26, видалити всі дані
зі старого хостингу. Автоматичне очищення не налаштоване. Перед фактичним
видаленням окремо узгодити точний склад даних і ресурсів, перевірити актуальну
резервну копію VPS та можливі розбіжності старої бази. Ця дата не є дозволом
мовчки запускати незворотне видалення. Відключення старих інтеграцій і служби
також виконувати окремо, не зачіпаючи інші ресурси облікового запису.
